
## 整体思路

明确目标 → 建立基线 → 多维度审阅 → 形成风险报告 → 制定架构目标 → 分阶段重构 → 用测试和指标验证

最重要的区别是：
**不要在没有基线、没有测试、没有性能数据、没有接口边界的情况下开始重构。**

否则你会遇到几个典型问题：

1. 改完不知道有没有破坏旧功能。
2. 性能变好还是变差只能凭感觉。
3. 架构越改越“抽象”，但复杂度没有下降。
4. 把旧代码的问题搬进了新架构。
5. 代码变漂亮了，但软件没有更稳定、更易维护、更专业。

## 定义“专业化目标”

这份软件要成为哪一类专业软件？不同目标的重构重点完全不同。

如果它像 **Linux kernel**，重点是：

- 稳定接口
- 硬件/系统边界
- 并发、内存、错误路径
- 兼容性
- 可维护的子系统边界
- 严格审查流程

如果它像 **PipeWire**，重点是：

- 清晰的对象模型
- 图结构/数据流模型
- 低延迟
- 插件化
- 会话管理与策略分离
- 多进程/客户端边界

PipeWire 的设计里，媒体流不是随意堆函数，而是被建模为 graph、node、port、link；node 负责处理媒体数据，port 表示输入输出接口，link 连接端口形成数据流。这种清晰模型是专业系统软件的重要特征。

如果它像 **FFmpeg**，重点是：

- 编码/解码/格式处理边界
- 严格的 C API 设计
- 回归测试
- 损坏输入测试
- 性能基准
- 内存安全
- ABI/API 兼容性
- 跨平台构建

FFmpeg 开发文档要求代码不能崩溃、不能泄漏内存、不能有数据竞争、不能依赖未定义行为，并且要求把来自文件、网络或调用者的字节流视为不可信输入；它还要求补丁通过回归测试，性能敏感改动要提供 benchmark，不能混合功能修改和纯格式修改。

所以你要先把目标写成一句话，例如：

> 目标不是“把代码写漂亮”，而是把这份软件重构成一个边界清晰、可测试、可扩展、性能可度量、错误可恢复、接口可长期维护的系统级软件。


## 代码审阅

### 1. 功能边界审阅

先不要看实现，先看这个软件到底承诺什么。

你要审阅：

- 核心功能是什么？
- 哪些功能是主路径？
- 哪些功能是历史包袱？
- 输入是什么？
- 输出是什么？
- 错误如何表达？
- 哪些行为必须保持兼容？
- 哪些行为可以废弃？

输出物应该是：

> 功能地图 + 主流程图 + 输入输出契约 + 兼容性清单

这一步非常关键。没有功能边界，重构就是盲改。

### 2. 架构边界审阅

看模块之间是不是有清楚的责任划分。

重点审阅：

- 哪些模块是核心？
- 哪些模块只是适配层？
- 哪些模块混合了业务逻辑、I/O、状态管理、错误处理？
- 模块之间是单向依赖还是循环依赖？
- 有没有“上层调用下层，下层又偷偷调用上层”的情况？
- 有没有全局状态到处被访问？
- 有没有本该是接口的地方写死成具体实现？

输出物应该是：

> 模块依赖图 + 分层图 + 循环依赖清单 + 待拆分模块清单

专业软件很少是“函数堆叠”。它通常有稳定核心、适配层、工具层、平台层、测试层、扩展层。

### 3. 核心抽象审阅

这是最重要的一步。

你要找出这份软件真正的“领域对象”。

例如：

- PipeWire 的核心抽象是 graph、node、port、link。
- FFmpeg 这类系统的核心抽象可能是 codec、format、packet、frame、filter、context。
- 一个网络库的核心抽象可能是 connection、stream、buffer、event loop、protocol parser。
- 一个数据库系统的核心抽象可能是 page、record、transaction、index、plan、executor。

你要问：

- 现在代码里有没有核心抽象？
- 抽象是不是稳定？
- 抽象是不是只是类名好看，但职责混乱？
- 有没有一个对象承担太多角色？
- 有没有多个概念被塞进同一个结构体/类？
- 有没有同一个概念在多个模块重复实现？

输出物应该是：

> 领域模型图 + 核心对象职责表 + 错误抽象清单 + 状态机图

专业软件的重构，核心不是“换目录结构”，而是**重新建立正确的抽象模型**。

### 4. 数据流与控制流审阅

你要画清楚数据怎么流动，控制权怎么转移。

重点看：

- 数据从哪里进入？
- 经过哪些阶段？
- 谁拥有数据？
- 谁修改数据？
- 数据什么时候释放？
- 是否有隐式副作用？
- 是否有回调地狱？
- 是否有反向调用导致控制流混乱？
- 是否有隐藏的同步/异步边界？

输出物应该是：

> 数据流图 + 生命周期图 + 控制流图 + 关键状态迁移图

底层软件尤其要重视这一点。很多 bug 不是因为某个函数写错，而是因为数据生命周期和所有权不清楚。

### 5. API / ABI / 接口审阅

如果这份软件有外部用户，接口必须单独审阅。

重点看：

- 哪些 API 是公开的？
- 哪些只是内部接口？
- 是否混用了 public 和 private API？
- API 是否暴露了内部实现？
- 错误码是否稳定？
- 结构体是否可扩展？
- 是否允许未来增加字段？
- 是否有版本策略？
- 是否有废弃策略？
- 是否需要保持二进制兼容？

Linux kernel 文档特别强调，用户态 ABI 一旦导出，就必须长期支持，因此接口设计必须经过充分思考、清晰文档和广泛审查。FFmpeg 文档也强调 release branch 的兼容性，点版本要保持源码和二进制兼容。

输出物应该是：

> 公共接口清单 + 内部接口清单 + 兼容性风险表 + API 改造计划

### 6. 错误处理与恢复能力审阅

这是区分“玩具项目”和“专业项目”的关键。

你要审阅：

- 每个可能失败的操作是否检查返回值？
- 内存分配失败怎么办？
- 文件打开失败怎么办？
- 网络中断怎么办？
- 输入损坏怎么办？
- 部分初始化失败如何回滚？
- 多步骤操作失败后资源是否释放？
- 错误码是否能定位问题？
- 日志是否能帮助调试？
- 是否存在直接 abort、panic、exit 的滥用？

FFmpeg 的开发政策要求检查并向上传递错误码，并把文件、网络或调用者传入的字节流当作不可信输入处理。Linux kernel 文档也强调要检查可能失败的操作，并使用 fault injection 测试错误恢复路径，因为未测试的错误路径往往就是坏代码。

输出物应该是：

> 错误路径清单 + 资源回滚策略 + 错误码规范 + 故障注入测试计划

### 7. 内存、资源、生命周期审阅

如果是 C/C++/Rust/系统级软件，这一项非常重要。

重点看：

- 谁分配？
- 谁释放？
- 谁拥有？
- 谁借用？
- 是否有 double free？
- 是否有 use-after-free？
- 是否有泄漏？
- 是否有隐式全局缓存？
- 是否有 fd/socket/handle 泄漏？
- 是否有跨线程生命周期问题？
- 是否有临时对象被异步任务引用？

输出物应该是：

> 所有权模型 + 生命周期图 + 资源泄漏风险清单 + RAII/cleanup 方案

如果是 C 项目，可以考虑统一 cleanup 标签、引用计数规则、对象状态枚举、allocator 规范。
如果是 C++ 项目，可以考虑 RAII、智能指针、move-only ownership、明确禁止裸 owning pointer。
如果是 Rust 项目，则重点检查 unsafe 边界、Send/Sync、生命周期绕过、FFI 资源释放。

### 8. 并发与异步模型审阅

专业软件必须有清楚的并发模型。

你要审阅：

- 是单线程事件循环？
- 多线程 worker？
- actor 模型？
- callback 模型？
- lock-based？
- lock-free？
- 哪些对象跨线程？
- 哪些对象只能在特定线程访问？
- 锁的顺序是什么？
- 是否可能死锁？
- 是否有数据竞争？
- 是否有 backpressure？
- 队列满了怎么办？
- shutdown 时怎么停止线程？

Linux kernel 文档提到 lockdep 这类工具可以提前发现复杂锁顺序导致的死锁场景，并建议非平凡锁代码在提交前启用相关检查。FFmpeg 也明确要求库在多线程和多个独立调用者同时使用时仍然正确。

输出物应该是：

> 线程模型文档 + 锁顺序表 + 共享状态清单 + shutdown 流程图 + 并发测试计划

### 9. 性能审阅

性能不能靠猜。

你要先建立基准：

- 启动时间
- 吞吐量
- 延迟
- 内存占用
- CPU 使用率
- 分配次数
- I/O 次数
- 锁竞争
- cache miss
- 热路径耗时
- 大输入/坏输入下的表现

审阅时重点看：

- 热路径是否有不必要分配？
- 是否频繁复制大对象？
- 是否有 O(n²) 算法？
- 是否把慢操作放进实时路径？
- 是否过度抽象影响热点性能？
- 是否有不必要的锁？
- 是否有不必要的格式转换？
- 是否有重复解析、重复编码、重复查表？

FFmpeg 的补丁清单要求：如果改动涉及速度关键代码，要做 benchmark，并在提交中提供结果。PipeWire 的设计目标也明确包括高效处理 raw video、用共享 ringbuffer 处理音频、支持低延迟处理。

输出物应该是：

> 性能基线报告 + 热点函数列表 + 内存分配报告 + benchmark 套件 + 性能预算

### 10. 测试体系审阅

没有测试保护网，不要大重构。

你要审阅：

- 是否有单元测试？
- 是否有集成测试？
- 是否有回归测试？
- 是否有 fuzz test？
- 是否有性能测试？
- 是否有损坏输入测试？
- 是否有并发测试？
- 是否有兼容性测试？
- 是否有 golden files？
- 是否有 CI？
- 测试是否稳定？
- 测试是否覆盖主路径和错误路径？

FFmpeg 明确要求提交前至少确认没有破坏已有行为，通常运行 FATE 回归测试；它还支持覆盖率可视化，并提供 Valgrind 相关工具链来检查内存问题。

输出物应该是：

> 测试矩阵 + 覆盖率报告 + 回归用例清单 + fuzz 输入语料库 + CI 门禁规则

你的重构应该先做这件事：

> 把当前行为固定下来。

也就是建立 golden tests。
即使旧行为不完美，也先记录下来。否则你后面无法区分“修复 bug”和“破坏兼容”。

### 11. 可观测性与调试能力审阅

专业软件不仅要能跑，还要能查问题。

你要审阅：

- 日志是否分级？
- 错误信息是否包含上下文？
- 是否有 trace？
- 是否能打开 debug 模式？
- 是否能导出内部状态？
- 是否能定位性能问题？
- 是否能复现线上问题？
- crash dump 是否有用？
- 关键状态变更是否可追踪？

输出物应该是：

> 日志规范 + trace 点设计 + debug 命令/接口 + 诊断文档

专业项目通常会让维护者在没有 IDE、没有完整上下文、只有日志和 core dump 的情况下也能定位问题。

### 12. 工程流程审阅

最后要审阅项目流程，而不是只看代码。

重点看：

- 构建系统是否清晰？
- 是否可重复构建？
- 是否有格式化规则？
- 是否有静态检查？
- 是否有代码审查规则？
- 是否要求小补丁？
- 是否禁止混合功能修改和格式修改？
- commit message 是否有规范？
- release 是否有流程？
- changelog 是否可靠？
- issue 是否可追踪？
- 维护者边界是否明确？

FFmpeg 的开发文档包含 coding rules、development policy、patch submission、review process、regression tests、maintainers、release process 等内容；这说明专业项目的质量不是只靠代码，而是靠一整套长期维护流程。

输出物应该是：

> CONTRIBUTING.md + coding style + review checklist + release checklist + maintainer map

## 审阅报告应该怎么写

不要写成“这个文件很乱、这个函数太长”这种主观报告。
应该写成能指导重构决策的工程报告。

建议结构如下：

### 1. 项目现状摘要

写清楚：

- 项目目标
- 当前架构
- 主要模块
- 核心流程
- 外部接口
- 已知问题
- 最大风险

### 2. 架构地图

包含：

- 模块依赖图
- 数据流图
- 状态机图
- 线程模型图
- API 边界图
- 资源生命周期图

### 3. 问题分级![[wifi_test_refactor_review]]

每个问题按严重程度分类：

|等级|含义|例子|
|---|---|---|
|P0|会导致崩溃、数据损坏、安全风险|越界访问、use-after-free、数据竞争|
|P1|会阻碍架构演进|循环依赖、全局状态、接口泄漏|
|P2|会增加维护成本|重复代码、命名混乱、错误处理不一致|
|P3|局部可读性问题|函数过长、注释缺失、格式不统一|

### 4. 问题按主题聚类

不要按文件列问题，而要按根因聚类：

- 架构边界不清
- 错误处理不一致
- 生命周期不明确
- 并发模型不清
- 测试缺失
- 性能热点未隔离
- API 暴露内部实现
- 构建和发布流程薄弱

### 5. 重构机会点

每个机会点写成：

- 当前问题
- 影响范围
- 推荐方案
- 风险
- 迁移步骤
- 验证方式
- 成功指标

例如：

> 当前 decoder 模块同时负责输入解析、状态维护、内存分配和错误恢复，导致测试困难、错误路径重复。建议拆为 parser、state、buffer、decoder_core 四层。第一阶段只抽 parser 接口并补 golden tests；第二阶段迁移错误处理；第三阶段优化热路径。成功指标是测试覆盖主路径和损坏输入，性能不低于当前基线。



## 根据报告找重构方向时，优先级怎么定？

不要按“哪里丑”来改。
按这几个优先级来排：

### 第一优先级：行为保护

先补测试、基准、日志。
没有保护网，不动核心逻辑。

### 第二优先级：边界切分

先把模块边界切开。
比如把 I/O、解析、核心算法、状态管理、平台适配、日志、配置分开。

### 第三优先级：核心抽象

找到真正稳定的领域模型。
不要过早做“大而全”的抽象。

### 第四优先级：错误处理和生命周期

把资源管理、失败回滚、错误码、对象状态统一起来。

### 第五优先级：性能热点

只优化测出来的热点。
不要凭感觉改性能。

### 第六优先级：接口稳定化

把 public API 和 internal API 分开，建立版本策略。

### 第七优先级：工程化流程

加入 CI、静态分析、格式化、review checklist、release checklist。

## 重构路线建议

我建议用 5 个阶段。

### 阶段 0：冻结现状

目标：知道当前软件到底是什么状态。

要做：

- 能稳定构建
- 能跑主要功能
- 补 smoke tests
- 建 golden tests
- 建性能 benchmark
- 记录当前 API 行为
- 记录已知 bug
- 记录兼容性要求

产出：

> baseline report

这一步完成前，不建议大改。

---

### 阶段 1：清理工程地基

目标：让项目可维护。

要做：

- 统一构建系统
- 统一目录结构
- 引入格式化工具
- 引入静态检查
- 打通 CI
- 分离测试代码
- 分离 examples / tools / core / platform
- 加最小开发文档

注意：
这一阶段不要做大规模逻辑改动。
Linux kernel 文档也提醒，不要为了风格本身做纯格式化改动；更好的方式是在真正修改相关代码时顺手改善。

---

### 阶段 2：切模块边界

目标：把混乱依赖变成可管理依赖。

常见拆法：

app / cli / daemon
        ↓
public API
        ↓
core engine
        ↓
domain modules
        ↓
platform / io / memory / threading
        ↓
third-party / system

或者多媒体/流处理软件可以考虑：

input
  ↓
demux / parse
  ↓
packet / frame
  ↓
process / filter / encode / decode
  ↓
output

或者像 PipeWire 这种图模型：
graph
  ├── node
  ├── port
  ├── link
  ├── scheduler
  ├── policy
  └── client/session
关键原则：

> 先让依赖方向正确，再追求代码优雅。

---

### 阶段 3：重建核心抽象

目标：让系统有专业软件的“骨架”。

你要定义：

- 核心对象
- 对象生命周期
- 状态机
- 错误模型
- 线程模型
- 内存模型
- 插件模型
- 扩展点
- public/private API

这一步最难。
它决定项目未来五年是不是还能维护。

建议你每个核心抽象都写一页设计文档：

```
对象名称：职责：不负责什么：生命周期：线程安全规则：错误处理规则：与其他对象关系：公开 API：内部 API：测试策略：未来扩展点：
```

---

### 阶段 4：增量迁移

目标：一块一块替换，而不是一次性推倒。

方法：

- 先包一层 facade
- 旧实现继续工作
- 新实现逐步替换旧实现
- 每替换一块就跑测试和 benchmark
- 保持小 patch
- 不混合格式化和功能修改
- 每次改动都有明确目标

FFmpeg 的补丁清单明确要求改动要尽量小，不能把功能改动和 cosmetic 改动混在一起；这对大型重构尤其重要。

---

### 阶段 5：稳定化和发布

目标：让重构结果可以长期维护。

要做：

- 完善文档
- 完善测试
- 删除旧路径
- 固化 API
- 建立 release notes
- 建立兼容性测试
- 建立贡献规范
- 建立维护者边界
- 建立性能回归门禁

到这里，才算真正接近专业项目。

## 判断重构是否成功的标准

不要用“代码看起来更舒服”作为成功标准。
建议用这些指标：

|维度|成功标准|
|---|---|
|构建|一键构建，依赖清楚，可重复|
|测试|主路径、错误路径、回归测试都有覆盖|
|性能|关键 benchmark 不退化，热点可解释|
|架构|模块依赖单向，核心抽象稳定|
|API|public/internal 边界清楚|
|错误处理|所有失败路径可恢复、可定位|
|内存/资源|无明显泄漏、悬挂引用、重复释放|
|并发|线程模型、锁顺序、shutdown 规则清楚|
|可观测性|日志、trace、debug 工具能定位问题|
|文档|新人能理解架构和贡献流程|
|发布|有版本策略、changelog、兼容性说明|

## 最容易犯的错误

### 1. 一上来重写

这是最大风险。
重写会让你丢掉旧代码里隐藏的业务规则、兼容行为和边界处理。

### 2. 把“抽象多”误认为“架构好”

Linux kernel 文档明确提醒，过度或过早抽象和过早优化一样有害。抽象应该只做到需要的程度，不要为了未来想象中的灵活性增加层数。

### 3. 只改目录结构

目录变漂亮不等于架构变好了。
真正的架构改善是依赖方向、生命周期、错误模型、数据流变清楚。

### 4. 没有测试就动核心逻辑

这会让你无法判断重构是进步还是破坏。

### 5. 混合格式化和功能修改

这会让 review 变困难，也会让 bug 难以定位。FFmpeg 的补丁清单明确要求不要混合功能修改和 cosmetic 修改。

### 6. 凭感觉优化性能

性能必须有 benchmark。
没有数据的性能优化通常是在制造复杂度。

### 7. 忽视错误路径

专业软件大量质量差异体现在错误路径，而不是 happy path。

## 建议

你的方法方向是正确的，但应该升级成更专业的路线：

> 不要先“全面重构代码”，而是先“全面审计系统”。
> 不要先追求漂亮架构，而是先建立行为基线、测试保护网和风险地图。
> 不要按文件改，而要按架构边界、核心抽象、错误模型、生命周期、性能数据来改。
> 不要一次性推倒，而要小步迁移、持续验证。

真正专业的重构目标应该是：

```
可理解 可测试 可调试 可扩展 可维护 可测量 可兼容 可发布
```
