# Root Cause 与 Workaround 判定

用于区分观测插桩、诊断实验、workaround/mitigation、行为型修改和 root-cause fix。目标是防止把“现象恢复”误写成“根因已修复”。

## 临时改动分类

- **观测型插桩**：只增加日志、trace、dump 或断言，不改变系统行为。必须有唯一标记，例如 `[DEBUG-AI]`，方便最后清理。
- **诊断实验**：为验证假设临时改变配置、调用方式、启动顺序或运行条件。必须写明本轮唯一变量和回滚方式。
- **workaround/mitigation**：绕过问题、重试、重启、重新初始化、降级或规避路径，让现象暂时消失。必须写明它绕过了什么、没有证明什么、保留期限和退出条件。
- **行为型修改**：会改变逻辑、时序、配置、默认值、返回值或错误处理路径。每次只能引入一个，用来验证一个具体预测。

## Root Cause 证明标准

宣称 root cause 前，必须满足：

1. 能解释原始失败现象；
2. 能解释 known-good / known-bad 对比；如果没有条件建立该对比，必须说明原因、替代证据和剩余风险；
3. 有红/绿闭环证明该机制对应的改变会影响目标症状；
4. 已排除至少一个主要竞争假设，或说明为什么无法排除；
5. 去除无关诊断变量后仍然成立，或明确列为剩余风险；
6. workaround 与 root-cause fix 已明确区分。

如果只能证明重试、重启、重新初始化、延时、降级或绕过路径后可恢复，只能称为 workaround/mitigation，不能称为 root cause。
