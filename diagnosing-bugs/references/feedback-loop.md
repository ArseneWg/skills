# 红/绿闭环

阶段 1 的目标是建立一个能捕获用户确切症状的最短反馈循环。没有这个闭环，不进入根因假设。

## 常见闭环

1. 用户提供的复现输入或步骤：把用户现象转成可重复执行的最短动作。
2. 失败测试：选择能触达该 bug 的单元、集成或端到端测试。
3. CLI 调用：固定样例输入，比较 stdout、stderr、退出码或产物。
4. 日志、dump 或 trace 回放：保存真实失败样本，在隔离路径中回放或复查。
5. 局部 harness：在可疑模块、函数、驱动入口或设备命令附近重建调用路径。
6. 性质测试或模糊测试：对随机、边界或不稳定输入提高失败复现率。
7. 二分定位脚手架：自动化“切到状态 X、启动、检查、重复”。
8. 差分验证闭环：同一输入分别跑旧版本和新版本、两套配置或两组数据。

## 优化循环

- 更快：缓存配置、跳过无关初始化、缩小测试范围。
- 更明确：断言具体症状，不只断言“未崩溃”。
- 更确定：固定时间、随机种子、环境、输入和依赖状态。

对非必现问题，目标不是一次干净复现，而是提高复现率。循环执行、增加压力、缩小时序窗口或插入等待点，直到它足以支撑调试。

## 完成标准

- 变红能力：能执行实际错误路径并捕获用户的确切症状。
- 确定性：每次运行结果一致，或不稳定问题有足够高复现率。
- 快速：耗时以秒计，或已说明为什么无法再缩短。
- 可重复：智能体可无人值守运行；人工参与仅需通过 `scripts/hitl-loop.template.sh` 或明确步骤。
