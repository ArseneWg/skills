# 诊断 Bug

这是一套用于快速诊断并修复棘手 Bug 的工作纪律。速度来自短反馈闭环、必要的上下文理解和清晰证据链，而不是跳过验证、提前下结论或先写补丁。目标是复现问题、收敛变量、验证根因，并交付可回归验证的最小修复。

## 硬规则

- **可以按问题复杂度选择轻量或完整流程，但不能降低证据要求。除非明确说明阻塞原因和风险，否则不得跳过红/绿闭环、假设公开、单变量验证、无效修改回滚和原始问题复验。**
- 没有诊断闭环，不要宣称 root cause。
- 没有理解相关模块的流程、设计意图和影响面，不要判定代码错误或提交修复。
- 假设必须有事实来源，并且可以被验证或排除。
- 一次只验证一个假设，一次只引入一个会改变行为的修改。
- 任何被证明无效的行为修改、临时补丁或配置改动，必须立即删除或回滚；绝不能在无效修改之上继续验证下一个猜想。
- 修复必须追溯到已验证的失败机制。
- 临时 workaround 不能冒充正式修复。
- 修完必须重新验证原始问题，并确认没有破坏已知正常路径。

## 强制门禁

使用本 skill 时，维护显式阶段状态，不能只在内部记忆中跟踪。状态只能使用：`未开始`、`进行中`、`通过`、`部分通过`、`阻塞`。

轻量流程仅适用于：症状单一、闭环短、边界清楚、假设很少、无需跨回合记录。轻量只减少展示和持久化，不减少红/绿闭环、公开假设、验证和复验。命中外部系统/硬件、跨边界、不稳定复现、多假设、行为型实验、方向变化、用户质疑、跨回合或准备交付任一项，使用完整流程并维护诊断审计轨迹；拿不准时按完整流程。完整模板见 `references/audit-trail.md`。

假设、预测和排除结果必须对用户可见；不得只在内部推理中维护。用户质疑方向、流程、结论或为什么改变判断时，先展示阶段状态和诊断审计摘要，再继续技术分析。

进入修复前，先写清楚阶段 1 的红/绿闭环：

- 失败特征是什么；
- 什么条件下会出现；
- 修复后用什么方式证明同一症状消失。

只要以下任一项未满足，不得使用“完成”“都做完了”“已解决”等完成类措辞：

- 原始红/绿闭环未通过；
- known-good 路径未验证，或未明确说明无法验证；
- 临时修改、调试配置、一次性脚本或运行时状态未清理，且未明确说明保留原因；
- 阶段 6 交付字段未完整填写；
- 未覆盖项和剩余风险未明确列出。

当用户询问“是否严格按步骤”“哪一步没做”“为什么没遵守”“有没有按 skill”这类流程合规问题时，停止继续推进技术细节，先做合规差距审计。审计必须用表格列出：

| 阶段  | skill 要求 | 已有证据 | 状态  | 缺口  |
| --- | -------- | ---- | --- | --- |

## 阶段 1：建立最短诊断闭环，构建反馈循环

先把用户现象转成可运行的红/绿判定信号。闭环必须捕获用户的确切症状，而不是只证明“没有崩溃”。没有红/绿闭环或明确阻塞说明，不进入根因假设。

闭环可以是测试、CLI、日志/trace 回放、局部 harness、差分验证、设备实验或其它可重复检查。复杂闭环、非必现问题和循环优化方法见 `references/feedback-loop.md`。

阶段 1 完成标准：已经至少运行过一次该闭环，并确认它能变红、足够确定、足够快、可由智能体或明确人工步骤重复执行。

如果受外部设备、人工操作、耗时实验或环境权限限制，暂时无法完整建立闭环，可以把阶段 1 标记为`部分通过`或`阻塞`。必须说明阻塞原因、已有替代观测、下一步如何补齐闭环和当前风险；此时只能做最小必要的上下文调查来建立闭环或缩小边界，不能宣称 root cause。

## 阶段 2：复现并收敛变量

运行阶段 1 的闭环，确认它对用户描述的症状变红。

**确认**
- 这个循环产生了**用户**描述的故障模式——而不是恰好出现在附近的另一个不同故障。错误的 bug = 错误的修复。
- 该故障在多次运行中均可复现（对于非确定性 bug，可复现的概率足够高以支持调试）。
- 你已经准确捕捉到了具体症状（错误信息、错误输出、运行缓慢等问题），以便后续阶段能够验证修复措施是否真正解决了问题。
**精简**
- 每次只改变一个变量。对于偶现问题，目标不是一次复现，而是提高复现率：循环执行、增加压力、固定条件、并行运行或缩小时序窗口，直到它足以支撑调试。
- 为何要这么做：最小可复现示例能缩小第三阶段的假设范围（减少需要怀疑的变动部分），并在第五阶段成为清晰的回归测试。
- 完成时，所有剩余元素都应是必要触发条件；移除任意一个，闭环就应变绿或不再复现。
只有完成复现**并**最小化处理后，才能进入根因假设。若外部条件阻塞，必须标记`部分通过`或`阻塞`，说明风险，并只做用于补齐复现、最小化或边界分层的最小调查。

## 阶段 2.5：系统边界分层

进入具体根因假设前，先把失败路径放到一条执行链上。目标不是列全所有可能层，而是用最少对比实验，把问题压到当前最窄边界。跨进程、跨服务、跨依赖、跨运行时、跨平台或跨外部系统的问题，不能直接在最熟悉的代码层修补。

边界分层可以和阶段 2 的复现收敛交替进行；进入阶段 3 前，必须收敛出当前最窄怀疑边界。

先写出当前失败链路，例如：

> 用户入口 -> 上层服务/任务 -> 核心逻辑 -> 依赖/集成层 -> 运行环境/配置 -> 外部系统或硬件

然后从外到内做边界压缩：

- 同一输入换入口：判断问题是否只在某个入口。
- 绕过上层封装，直接调用底层能力：判断问题是否已经下沉。
- 分阶段执行，替代端到端执行：判断失败发生在哪一段。
- 对比运行时真实状态和声明配置/源码：判断是否是配置未生效、状态漂移或部署产物问题。
- 临时禁用、mock 或替换某个依赖：判断问题是否来自外部依赖或集成层。
- 对比 known-good / known-bad：确认边界差异是否稳定解释现象。

每个实验只回答一个问题：这个边界以上是否已经可以排除，问题是否下沉到下一层，当前最窄怀疑边界是什么。

完成标准：

- 已写出失败执行链；
- 已记录排除掉的上层边界和负证据；
- 已写明当前最窄怀疑边界；
- 下一阶段假设必须绑定到这个边界。

当问题涉及嵌入式、kernel driver、suspend/resume、wake、power domain、pinctrl、regulator 或外设总线时，读取 `references/embedded-suspend.md`。

## 阶段 3：基于上下文提出可证伪假设

阶段 3 的目的不是凭空猜原因，而是基于已观察到的症状、最小差异、日志、配置、版本信息，以及对相关模块流程和设计意图的理解，提出可验证的候选原因。

重要约束：先不要修改目标行为；没有运行时证据前，不要直接给修复方案。

在列出假设前，先建立对问题相关模块的足够理解：

- 先通过代码搜索和阅读，确定 bug 的入口和最小调用链。
- **优先看下代码最近的修改，最近的补丁patch，最近的提交，然后再深入其他部分。**
- 调研相关路径、最近变更和调用链；优先定位与复现步骤、错误现象、日志、堆栈，不扩大成全仓审计。
- 经过哪些关键流程、状态转换或系统边界；
- 失败点上下游的调用关系；
- 相关配置、版本、数据或外部条件；
- 被怀疑代码原本的设计意图、兼容职责或保护作用。

不要把尚未理解的代码直接判定为错误。一个好的假设应该解释“为什么这段原本合理的逻辑，在当前条件下导致了失败”。

通常列出 2 到 5 个按可能性排序的假设。每个假设必须包含：

- 支持它的已观察事实；
- 涉及的代码路径或系统边界；
- 怀疑的失败机制；
- 可观察预测；
- 验证或排除它的方法。

进入阶段 4 前，必须先把将要验证的假设显式展示给用户。简单问题至少展示 1 个当前假设；复杂问题展示 2 到 5 个候选假设，并按可能性排序。每个假设使用稳定编号，例如 `H1`、`H2`，后续诊断实验记录必须引用这个编号。

推荐格式：

> H1: 基于 ____ 现象，我怀疑 ____ 路径中的 ____ 机制导致问题。
> 如果它是真的，那么 ____ 应该出现 / 消失 / 变得更严重。
> 我将通过 ____ 来验证。

如果一个假设没有事实来源，或者不能导出预测，它只是感觉，不足以进入插桩或修复。

## 阶段 4：验证假设并定位根因

没有先向用户展示阶段 3 假设，不得进入验证、插桩、配置变更或行为型修改。若新证据产生新假设，先回到阶段 3 展示新假设，再验证。

每一次插桩、实验或对比都必须对应阶段 3 中的某个具体预测。一次只验证一个假设，一次只改变一个变量。

优先使用能直接区分假设的观测方式：debugger、trace、定向日志、状态 dump、版本差分、配置差分、输入输出差分、性能基线或 profiler。不要“把所有东西都打日志，然后再 grep”。

区分观测插桩、诊断实验、workaround/mitigation 和行为型修改。行为型修改每次只能引入一个，用来验证一个具体预测；分类标准和 root cause 证明标准见 `references/root-cause.md`。

如果行为型修改证明无效，必须立即回滚到干净基线，再验证下一个假设。不要叠加多个无效修改；不要在失败实验留下的代码上继续修改。

对于性能问题，先测量，再修复。先建立基线、热点位置和退化幅度，再判断原因。

阶段 4 的输出应该是以下两种之一：

- 某个假设被证据验证，并能解释失败机制；
- 当前假设被排除，相关行为修改已回滚，需要带着新证据回到阶段 3。

如果证据只能说明某个 workaround 有效，但不能解释为什么有效，不要把它当成 root cause。宣称 root cause 前，必须按 `references/root-cause.md` 检查证明标准。

## 阶段 5：基于已验证根因修复

只有当某个假设已经被阶段 4 的证据验证，才进入修复。修复必须能追溯到这个已验证的失败机制。

如果修改过程中发现原假设不成立，或者需要依赖新的解释，停止修改，完整回滚当前无效修改，再回到阶段 3 或阶段 4。不要在无效补丁上继续叠加新补丁。

修改代码前，先理解被修改代码的原设计意图、调用方、兼容约束和影响面。不要因为某段代码触发了当前 Bug，就直接删除或重写它；它可能正在保护其他版本、配置、运行路径或异常场景。

修复原则：

- 做最小修改；
- 修改必须可解释、可回滚；
- 不顺手重构；
- 不改变无关路径；
- 优先保留兼容路径，用 guard、条件约束、版本判断或局部修正解决具体问题；
- 不把 workaround 冒充 root cause fix。

当多个诊断变量叠加后出现绿色结果，不得直接交付。必须反向删除无关变量，确认最小仍绿集合；如果时间或环境不允许，必须明确列为剩余风险。

如果存在正确的测试边界，先把最小复现固化为失败测试，再修复，并亲眼看它从失败变为通过。

如果不存在正确的测试边界，这本身也是发现。记录原因，并保留最接近真实问题的验证方式，例如诊断脚本、harness、trace replay、版本对比或固定复现步骤。

修复后必须重新运行阶段 1 的原始诊断闭环，并验证 known-good 路径没有被破坏。

## 阶段 6：验证、交付与复盘

宣布完成前，必须重新运行原始红/绿闭环，验证回归或替代路径，确认 known-good 路径没有被破坏，并清理或明确保留所有临时修改、调试配置和探针。

最终交付必须说明问题现象、影响范围、根因、修复方案、验证方式、known-good 路径、临时措施撤销情况、未覆盖项、剩余风险和复盘。完整交付清单见 `references/delivery.md`。
